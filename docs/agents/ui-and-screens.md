# UI, screens and sound

The title, the explorer run, sound, the menu stage and pixel-ui rules, cursors and pointers, the stage, keyboard ownership, frames, icons and the typeface.

Moved out of `AGENTS.md` on 9 Nov 2026 so that file stays small; nothing here was reworded. Keep it current the way `AGENTS.md` asks: a change that adds a subsystem or makes a note here untrue updates the note in the same change, and a new note goes in the doc whose area it belongs to.

## Notes

- **The title screen (`TitleScene.ts`) is the front page's banner come alive**, made of the game's own parts and nothing new: a band of Viridian City's real layers (`TITLE_TOWN`) drifting a pixel at a time under stepped dusk and a side vignette, sparkles, the name stamped out of Orange Kid itself into a gold logo (outline, rim and depth are the same lettering stamped again in other colours, into one canvas a slanted shine re-lights every few seconds), the README's tagline, and every fifteen seconds the trainer legging it along Viridian's main street - Red, or the save's own look once it has one (`SaveSummary.look`) - with the save's own partner (`SaveSummary.partner`, else a random starter) at their heel and Blue behind with his "!". What moves and when is `ui/titleScenery.ts` - pure functions of the time since the title appeared, every answer a whole pixel - and the menu redraws on its own so a keypress never rebuilds the town. `prefers-reduced-motion` gets the still picture. A device whose primary pointer is a finger and that has pressed no key (`input/keyboardSeen.ts`, watched from `main.ts`) opens on `keyboardMenu()` instead - the game needs a keyboard, for now, and has no touch controls; any key or the one row's tap takes it away for the page. The chase owns the bottom `CHASE_LANE` pixels, so the menu is laid out in the screen less that. `BootScene` paints the same dusk with a mint loading bar (no words: the font is still arriving) and the title fades in from it. Under the name it offers **CONTINUE, NEW GAME, and MAKE A MAP and PLAYTEST side by side on one row** (`ui/titleMenu.ts`, Phaser-free: the wording, the cursor rule and the layout - a choice marked `beside` takes the right half of the row before it; Up/Down walk reading order so every button is reachable, Left/Right only cross a row; `SaveManager.describe()` is what it reads - none, unreadable or a game with counts). MAKE A MAP opens the map maker and nothing else (the owner, 2026-10-10: the playtest button does not belong inside it). CONTINUE is dim and skipped by the cursor when there is no game to continue; a save the loader refuses is `unreadable`, never `none`, so it is not offered as empty; and **NEW GAME over any save asks first, with the cursor on KEEP MY GAME** (the key that woke the game is still down), because a save is never erased by one keypress. A browser that cannot write a save (`SaveManager.canSave()`) is told so on the starter screen instead of being offered a partner, because every later screen reads the game back out of the save and starting without one was a black screen. Space on a fresh browser still goes straight to Oak's table (`StarterScene` routes to it, next entry) and on a save straight to the lobby, which is what the playtest drivers rely on. There are deliberately no save slots for the ordinary game - `docs/screens/title-menu/README.md` says why - and the explorer run is not one: it is a second *file*, chosen on the way in and never listed beside a save (see the entry below). It is rebuilt on `RESIZE` and never scales a tile. It needs no font wait of its own - `BootScene` starts it only after `awaitGameFont()`. `tools/playtest/titleShots.mjs` photographs it in every state, and `--at=ms,..` steps its clock to exact moments; `docs/screens/title-dusk/` is the before and after.
- **The explorer run is a second game, not a difficulty.** `src/game/dev/playtestMode.ts` carries the whole of what the mode is and why; `playtestSave.ts` is the one save it deals. It exists so the maps can be *looked at* - four times the ground they shipped in, and a five-minute clock with a hunter on it is the opposite of a walk. Six things change and nothing else does. It is **its own save** (`PLAYTEST_SAVE_KEY`): `SaveManager` resolves its key per call through `activeSaveSlot()`, so every scene's argument-free `new SaveManager()` follows the live slot and no call site learned there are two; only `TitleScene` names a slot, to describe the other game without switching into it. The **player's side cannot be knocked out** - `hpAfterDamage()` in `battleEngine.ts` is the one function every path that takes HP goes through, and it floors the player at one; the flag is false everywhere else, which is what keeps `trainerMeasure.ts`, `encounterMeasure.ts` and the whole boss ladder reading exactly what they always read. The clock is `PLAYTEST_RAID_DURATION_MS` (eight hours, `HubScene.raidClockMs`) rather than stopped, so the hunter still arrives and the tiers still escalate - the escalation is measured from the raid's start, not from its length - and the chip says PLAYTEST instead of counting it down. **Every door is open and every keeper is still standing**: the doors go in `openedGates` as `gateKey(gate)` rather than into `defeatedBosses`, because a beaten boss is taken off the map (`withoutDefeatedBosses`) and fighting them is half the point - a trainer on an open door is walked up to, which `mapStructure.testkit.ts` already guarantees is payable. Every extraction is open (`WorldScene.isExtractionOpen`) and every tile of every map is surveyed, so the drop-in screen shows the country. And **shift walks three times faster**, in that mode only, because 150ms a tile across 64x72 is a long way to check a corner - taught on the objective chip's hint row beside `[O] GUIDE` and `[L] LOOK`, by the same rule the look is. The flag is a module variable and nothing stored: a reload lands on the title, which sets it back to `normal` on every ordinary path, so an explorer run is unreachable by accident by construction. Screens: `docs/screens/playtest-mode/`. **It carries a kit, one row a feature** (`dev/playtestKit.ts`): boxes of Pokémon each harbour game is played with (JUMPERS, PROMENADE, FIRST STAGES), 5,000 tickets, and `PLAYTEST_GAMES` - a new harbour game adds its row there with the kinds that suit it, and `playtestKit.test.ts` fails a game the save has no suited *and* no unsuited Pokémon for. The kit only adds and is applied to every resumed run too (`withPlaytestCurrent`), and marks every gym leader met, never beaten (`withEveryLeaderMet`), so each spars in the hall; a game that is a scene of its own is a `PlaytestGameScreen`. `?playtest` on the address goes straight in. The **PLAYTEST BOARD** (`dev/playtestBoard.ts`), a sign stamped on the lawn by the landing in that run only (solid only while it stands, so the ordinary yard's walks never see it), goes to any room or part of the harbour, sets the hour (`dev/playtestClock.ts`, which `windowLight` answers with in that run only - the harbour's light, its night people and a night raid all follow), starts a NEW DAY (the Game Corner's daily pays again) and opens any game; `tools/playtest/playtestKit.mjs` plays it.
- Background music stays off, as the captain's standing preference (2026-09-19: sound effects welcome, music "pretty annoying") rather than a temporary switch: `SILENCE_BACKGROUND_THEMES` in `src/game/audio/AudioManager.ts` makes `startTheme()` a no-op while sound effects keep playing. Leave it and the scene `startTheme` calls alone; a theme written for later ships silent.
- Every sound effect is a named entry in `SOUND_EFFECTS` in `src/game/audio/soundEffects.ts` - square, triangle, sawtooth and noise voices as data, no audio files - and `audioManager.play(name)` is the only way one is sounded (`playWaking(name)` is the same call for a key or click that may be the page's first: a browser keeps audio asleep until a press, and `play` never wakes it, so the title's sounds go through it). **The one exception to "no audio files" is a Pokemon's cry** (the owner's call on playtest 28, 2026-10-11): `cry` and `faintCry` are entries of a second kind (`CryEffect`, channel `cry`) played as `play('cry', { species: dexId })` from FireRed's own samples, `public/assets/cries/<dexId>.wav` (`scripts/fetch-frlg-cries.mjs` from pret/pokefirered, `audio/cries.ts`, provenance recorded). A cry neither cuts nor is cut by anything but a fanfare: it *waits* for the battle, fanfare and cry channels, which is what puts it after the ball's pop and after the catch fanfare, and two Pokemon sent out together cry in turn. `play()` never waits on the network - a cry whose sample has not arrived sounds its tone `standIn` - so a fight's cast is fetched ahead (`loadCries`, from `WorldScene.transitionToBattle` and `BattleScene.create`). Which event cries is `battleEventCry` and `openingLineSounds` in `battleSounds.ts`: every send-out (the opening `Go, X!` included), a wild Pokemon appearing, a faint (lower, FireRed's faint pitch) and a catch - and an evolution cries as FireRed's `evolution_scene.c` does, from `BattleScene`'s evolution beat: the old species at "is evolving!", the new one with the fanfare, the old one again if B stops it - and a stone used from the raid pack sounds the same fanfare and new cry (`BagScene.giveTo`). The mixing rules live in `play()` and nowhere else: a channel says one thing at a time, anything that is not `ui` cuts `ui` (so the blip of the key that advanced a line never lands on the hit the line describes), a fanfare cuts everything, and the same effect asked for twice within `RETRIGGER_GUARD_S` sounds once. Which event gets which sound is pure and tested beside it - `battleSounds.ts` (battle events, and `BattleNote` for narration that carries a sound), `worldSounds.ts` (the edge-triggered ones: bump, tall-grass entry, hunter proximity) and `menuSounds.ts` (the DOM menus' baseline click, applied once in `MenuOverlay`). `soundEffects.test.ts` fails an effect that is too long or loud for its channel, identical to another, or played by nothing. A sound cannot be reviewed from a diff: audition it on the Test Lab's sound board (`?test-lab=1`), and check "did that play twice?" against `__audio.recentlyPlayed` on a dev build, which records only what was actually heard. Every effect is a one-shot, so none can outlive its scene; do not add a looping one. **Music ducks under a sting**: themes sound through a music bus under the master, and an effect with `ducksMusic` (every fanfare by default, plus the four one-off alerts that opt in - never a rhythmic one, which would hold the music down through a whole chase) takes it to `DUCK_LEVEL` for the effect's own length; two in a row are one quiet stretch. It works on whatever is on the bus while music stays silenced, so the day a theme is wanted it already ducks (`__audio.musicLevel` reads it; `docs/screens/audio-ducking/`).
- **There are two boxes, and the menus are not in the canvas's one.** The world view is small on purpose; the DOM screens used to be pinned to the same box (`#app` was a CSS container and every screen measured itself against it), so a stash on a 4K display got exactly the room a stash gets on a laptop, only magnified - a list that did not fit became a scroll wheel whatever the display could do. `src/game/display/menuStage.ts` is the second box: `#screens`, a fixed layer beside `#app` that every `MenuOverlay` is appended to, sized against the *browser window* and carrying its own `--px`/`--zoom`. It is a sibling and not a child because `container-type` makes an element the containing block even for a fixed position. The rule it is built on is **room before magnification**: the scale steps up only once the window could hold a generous `MENU_STEP_*` screen at the next whole multiple (2x to 4x, never the canvas's 6x), and everything left over becomes game pixels - less `FEEDBACK_TAB_STRIP`, the 32 pixels the FEEDBACK tab stands in on the right (along the bottom of an upright phone, and of a window too narrow for the strip beside the smallest screen but tall enough for it underneath - `feedbackTabEdge`, the stylesheet's own rule; 640x480 has room on neither edge and keeps it on the right, except over a menu, where it stands in the corner of the help bar), so no menu is ever under the tab - bounded across by `MENU_MAX_WIDTH` (1120, a ceiling on how far the pane at one edge is from the pane at the other - the measure of a *row* is its column's, below). `stage.ts` and the canvas are untouched by any of it, which is what keeps everything world-anchored - the dialogue box, a world caption, the raid HUD - exactly where it was; `tools/playtest/worldAnchors.mjs` prints those positions so a change to either box can be diffed rather than eyeballed, and `tools/playtest/menuShots.mjs` photographs every screen at a real window size on a realistic save (two dozen Pokemon, twelve kinds of supply) and counts how many rows of each list a player can actually see; `--keys` walks the arrow keys over a screen laid out in columns and fails if any row of it cannot be reached without a mouse, which is the one thing a screenshot cannot show.
- **A collection fills the width it has, and one column is what a narrow window gets.** Every screen body was `minmax(0, 1fr)` and every list a single implicit track, so a wide display held a tall thin list down the middle with a scroll wheel on it - which is the fourth time the captain has raised crowding on these screens. A pane opts in with `data-columns` (`pixelColumns()` in `ui/pixelUi.ts`, carrying one of `COLUMN_MEASURES` - the narrowest a column of *that kind of row* may be, measured off the rows rather than chosen), `ui/columnLayout.ts` counts the tracks and `MenuOverlay.layoutColumns()` writes them, in the same measured pass that snaps text boxes - so a live resize relays the screen. **Every track is a whole number of game pixels**: the room left after the gaps is shared out one pixel at a time, first tracks first, because `repeat(n, 1fr)` lands on thirds of a pixel at most widths and draws every one-pixel frame in the list soft. Below two columns nothing is written at all, so a narrow screen is exactly the screen it was. `data-columns-max` and `data-columns-widest` make a centred row of cards instead of a stretched list (the starter picker, the lobby's three doors). Two things that follow: a generated box in a grid takes one *cell*, so the MORE strip carries `grid-column: 1 / -1` or it draws its rule across a third of the pane; and `align-items: start` is only on `.px-list[data-columns]` - a row of cards must stretch or three doors of different lengths stop reading as equal.
- **The collection and the answer about the thing in it are one screen.** A Pokemon's experience, stats and moves were a whole second view reached by a SUMMARY chip that stood on every stash row beside MOVE, TAKE and GIVE, so two dozen Pokemon were a hundred controls with the thing you came for a layer down. It is the PC box instead: a row is the two lines that tell one Pokemon from another, and everything about the one under the cursor - portrait, types, condition, gear, experience, stats, moves, and whatever deeds that screen offers - is `HubScene.pokemonDetail()` in the `.px-detail` pane under the list, the same pane the contract board and Brock's ladder use. The loadout's treatment chips are its `deeds`, for the same reason. **Every control inside a detail pane carries the pane's own `data-shows`**, or the cursor moving into it swaps the pane out from under itself. The dossier is as tall as what is in it, in a window that is a column flex (`:has(.px-dossier)` in `style.css`) so it can shrink to the screen: once list and dossier cannot both be whole the dossier gives way first, down to `--dossier-floor`, so how much of the list shows never depends on which row the cursor is on - a fixed band was one line and a MORE strip over half a screen of backdrop, with the raid party's TAKE below the fold (playtests 38 and 44); `roomFor()` in `columnLayout.ts` is the one rule that asks how much room the *screen* has (`data-room` on the overlay root, the only thing the stylesheet keys off it), because the band's five blocks need 820 game pixels to stand side by side and a band that wraps is a band cut through the middle. It is **three rungs, not two** - `tight` is `BASE_STAGE` itself, where a list, the band that answers for the row it is on *and* a second band under that cannot share one pane - so every `[data-room='narrow']` rule in the stylesheet carries a `[data-room='tight']` twin, held by `columnLayout.test.ts` because the failure is otherwise silent. `MenuOverlay.showDetailFor` swaps panes **within the control's own window**, not across the screen: Bill is two counters on one page, and swept screen-wide, pointing at his shelf blanked the pane under his barter table. Which window is `detailGroupOf`, not `closest('.px-window')` - a button or a chip wears that class too, so the nearest one to a chip is the chip, and a pane under the list stopped answering at all. `docs/screens/menu-columns/` is the before and after.
- **A shop says what a thing does, and says it whether or not you have bought it.** A workshop rung's subtitle used to be its *price* while unbought and its *effect* once built, so the one moment a player needs to know what a thing does - deciding whether to buy it - was the moment it was hidden, and the screen explained the purchase after the money was gone (the captain, 2026-09-20, having bought Secure locker I without knowing what it was). `src/game/ui/shopDetail.ts` is the rule both shelves render, Phaser-free: **the row's own line is always the effect**, because what a thing does is its identity and identity does not change when you pay for it; **the price is a column of its own on the right** (`shopPriceColumn`, one short line a part, red and marked with a drawn cross (`SHORT_MARK`, so short is a shape as well as a colour) on what this vault cannot cover, `COLUMN_MEASURES.priced`), which is how a shelf has always answered both at once; and the `.px-detail` pane under the list holds the whole picture for the row the cursor is on - the longer promise, the price **against what is actually spendable** (`payablePokemonCount`, `spendableSupply`, `moneyHeld`, the ration), and the gate, named. Nothing needed writing: `workshop.ts` already carried `effect` and `detail` and every item already carried a `description`, and the pane prints effect above detail, so a `detail` that restates its effect says one thing twice - `shopDetail.test.ts` fails either shelf for it. A bought rung keeps its line and its price column says PAID. Bill gets the same treatment on both counters, and his two irreversible deals - a barter and the berth - are **asked again before they are struck** (and so are Brock's rungs and the partner swap; the safe answer stands last, in the seat of the button that armed it, and `HubScene.clickedTooSoon` swallows a pointer click on the confirm within `RELEASE_ARMING_MS` of arming, because the second click of a double-click released a partner): the row becomes the question and two buttons with the cursor on the one that changes nothing, the arrows stay between its two answers (`askedDealIndex`), and while a deal is asking no other row carries `data-cursor-start` (`refocus` takes the first in the document, and a shelf row still carrying one bought a Poke Ball with the second press). His shelf is never armed: a Potion for Pokedollars is an ordinary purchase and already rationed. `tools/playtest/shopScreens.mjs` stands in front of a rung you can afford, one you cannot and one behind a door and asks all four questions with the arrow keys; `docs/screens/shop-screens/` is the before and after.
- **Every** DOM screen that belongs to the game is **pixel-ui** - lobby, starter picker, raid result, and since #156 the three a raid opens over the world (the pack, the party, the field guide): an overlay opts in with the `pixel-ui` class, its markup comes from `src/game/ui/pixelUi.ts` (`pixelScreen`, `pixelWindow`, `pixelCommitBar`, `pixelHpBar`, `pixelTag`, `pixelGrid`), and its styling is the `Pixel UI` block that ends `src/style.css`. The unit is one game pixel: `stageScaler.ts` sets `--px` (and the bare `--zoom`) on `#app`, the block calls it `--u`, and every measurement is `calc(var(--u) * N)` with `N` whole - never `px`, `vw`, `cqw` or `em`. One type size, 12.5 game pixels, because Orange Kid's stem is 0.08em and that is where a stem is one pixel, and no bold cut (`strong` is 400), so **weight and size are not levers and hierarchy is inversion, ink, a visible rule and space**. Three ranks, each the title bar or the window reused: `.px-title` is a dark strip 16 pixels deep across the whole screen (where am I); `.px-heading` is the same strip in miniature, 14 deep, bled out to its own window's frame with its note in `--bar-muted` (what is this panel); `.px-subheading` is a `--cream-dim` band across a list in full `--ink` caps, ruled off in `--frame`, with three times the room above it as below (what is this part of the list). Under them a name is plain caps in `--ink` and a detail is `--ink-soft`. Never `--cream-dim` for a rule - on `--cream` it is a twelve per cent step that reads as a fill, not a line - and never `--ink-soft` for a heading: that is de-emphasis. A DOM screen may draw on a canvas of its own - the drop-in screen's map is one - and `#app > canvas` is scoped to the game's own canvas for that reason: unscoped, its `max-height: 100%` resolved a picture inside a pane with no definite height to nothing at all. Nothing inside a screen may resize the screen: `.px-screen`'s one column is `minmax(0, 1fr)` and the title bar's aside clips, because a grid's `auto` column takes its floor from the widest child's min-content and the title bar's `nowrap` back label and aside pushed the lobby 19 pixels past the canvas at the smallest stage. `style.test.ts` holds all of that. **No glyph is ever half-drawn**: a `.px-heading` note is whole or not drawn (the strip wraps a note that does not fit onto a second line the one-line strip clips away, so a note is never itself clipped or shrunk - a note a player needs, like the final check's squares, must be short enough to fit the smallest stage), and a `.px-scroll` pane whose foot would cut a row through its waist gives the whole row to its MORE strip (`scrollCoverHeight()` in `MenuOverlay.ts`, set as `--more-cover` by `markScrollCues()`) and clips off a line *beside* that row the strip's edge would still cut (`foldedRows()`, `data-folded` - Bill's detail panes are two columns whose lines interlock, so no one fold is clean in both), and a row of wrapped copy that is not a control (the result screen's contract) is measured as its lines beside its icon (`rowPieces`), so the strip falls between two of them rather than taking the whole row and its heading, and a `.px-subheading` is never the last line above the strip - with its rows all below the fold it goes under the strip with them (`orphanedHeading`; the drop-in pane ended on ERRANDS over nothing) - and a scrolled pane's top edge masks out the sliver of a row it cuts, down to the first whole row (`scrollTopCoverHeight()`, `data-above`) - the cursor scrolls a row into view by just enough to show it, which left the row above sliced through its name. `tools/playtest/headingShots.mjs` photographs every headed screen at both stages and audits each strip's note by geometry (`docs/screens/heading-clip/` is the before and after). `docs/screens/menu-hierarchy/` is the before-and-after at 3x and at the smallest stage. Orange Kid has no arrows and no tick, so none may be typed - the cursor and the tick are drawn masks (`--px-cursor`, `--px-tick`) and a HubScene test fails a screen that types one. Text is the only thing whose width is not a multiple of the unit, so `MenuOverlay.snapTextBoxes()` widens text-sized boxes to the grid after every render - and again on `document.fonts`' `loadingdone`, because boot waits for Orange Kid only `GAME_FONT_TIMEOUT_MS` and boxes measured in the monospace fallback stayed a third too wide (the starter picker's two type tags stopped fitting on one row; `tools/playtest/browser.mjs`'s `page.on('Fetch.requestPaused')` holds the woff2 back to reproduce it) - and `.px-screen` is its own transparent layer because that is what makes Windows and Linux antialias the face in greys instead of LCD colour fringes. Every selector in that block is scoped to `.pixel-ui` - through `:where()`, so the scope adds no weight and the cascade reads as written - because the older screens share class names with the lobby; `style.test.ts` fails an unscoped one. The flip side: a `:where()`-scoped rule weighs one class, so it can never pad a window against `.pixel-ui .px-window` (two). Bill's tight `padding: 0` sat dead for a release for that reason, and `style.test.ts` now fails any rule like it. Brock's ladder and payment are pixel-ui too (a rung is a `px-tall` row, and what the pointed-at rung does is the list's one `px-detail` pane, as on the contract board). How far a Pokemon is from its next level and what each of its moves does are derived by `src/game/ui/pokemonSummary.ts` (the top of the experience curve is read off the curve, because `experienceForLevel` clamps, rather than from a second copy of the cap) and drawn in the stash's own detail pane - see the entry below; there is no summary *screen*. Only the Test Lab (`?test-lab=1`) is still the older rounded style, which is a dev tool and nobody's game. **A screen a raid opens is the same screen as the one at base**, and that is a rule rather than a resemblance: `raidScreens.test.ts` holds all three to the shared parts, to `pixelColumns`, to `moveCursor`, and to having no layer of their own. It is read under the clock with the hunter on the map, so a layer costs more here than anywhere - the bag's pocket *tabs* are gone (every pocket at once, banded by `.px-subheading`, gear among them for the first time), the row itself is the act (Enter on a Potion opens the recipient list, so using one is four presses) and the pointed-at item's squares are lit by a class on a block rather than by a re-render (`BagScene.markPack`, off the `data-describes` key every `pixelGrid` block carries - the same key its row does, so pointing at a square answers for the row and back). The pane under a list of Pokemon is one module, `src/game/ui/pokemonDossier.ts`, shared by the stash and the raid party so two lists of the same thing cannot drift into two shapes; its CSS is `.px-dossier*`. One trap it paid for twice: **a `.px-scroll` pane may never have bottom padding of its own**. A sticky MORE strip sticks to the *content* edge, so the padding shows the tops of the next line's letters under the very cue that exists to stop a row being half drawn - `.px-scroll` sets it to zero and `style.test.ts` fails a later rule that puts it back on any class the markup ever pairs with `px-scroll` - `.px-dossier` had it, and then `.shop-detail` did. A wrapped `.px-wrap` sentence is measured for the fold line by line (`lineBoxes()` in `MenuOverlay.ts`), so the strip may fall between two of its lines but never through one. And **a pane may never draw a scrollbar for a pixel**: Orange Kid's content area is deeper than its 12-pixel line, so a list's last row overflows its pane by a screen pixel, and where a browser draws scrollbars (Windows) that bar took the width its columns were counted in, a second took the height and the MORE strip the rest - the final check cut three rows through their middles over an empty screen. `fitsItsBox` marks such a pane `data-flush` and it clips instead; `menuShots.mjs --scrollbars` fails a pane that scrolls by a pixel or sideways, and only `--scrollbars` shows it in a picture.
- **A menu shows things rather than listing them** (the captain, 12 Nov 2026: menus "so cluttered and boring"; `docs/screens/menu-overhaul/` is the inventory, the named benchmarks, the rules and a before, after and scorecard per menu, redrawn one pull request at a time). - **On a screen whose rows are a choice of who receives something, the pointer only previews** (the captain, 2026-09-27: teaching a move, the mouse on its way to the button made whichever Pokemon it crossed the chosen one). `MenuOverlay.pointerRule = 'previews'` (`ui/pointerPreview.ts`, tested in `pointerPreview.test.ts`): the pointer draws a one-pixel rule round what it is over (`[data-pointer='previews'] button:hover`) and reads its help on the help bar, and only a click or the arrow keys move the cursor. - **Never redraw a screen from a focus event.** Setting `innerHTML` inside `focusin` throws away the control the cursor just landed on and the columns measured for it, and from inside `MenuOverlay.moveCursorTo` the unmeasured screen is what gets painted: the old starter picker did this and looped (the cards at their narrowest, no cursor, keys dead; `tools/playtest/starterBalls.mjs` samples every painted frame of the swap's cards under a real pointer). - A pixel-ui screen has one cursor, as the games it is dressed as do: `MenuOverlay` moves focus with the pointer (except where the rule above says it previews), `moveCursor()` walks the arrow keys by where controls are on screen (`src/game/ui/spatialFocus.ts`, Phaser-free and tested) - except that a vertical move stays inside the scrolling pane it started in while that pane has anything ahead in it (`FocusRect.group`), because a row below a pane's fold reports a position past the bottom of the screen and Down from the last visible row went to the bar under the pane instead, leaving supplies no arrow key could reach, **Tab** crosses between a row and the detail pane it shows (`detailStepIndex`, `leavingPaneIndex` - Up out of a pane returns to its row), because every row the arrows cross swaps the pane, so the arrows alone only ever reached the deeds of a column's bottom Pokemon (the dossier writes `· TAB` over where it lands - its deeds, or its moves when it has no deed to do), `refocus()` puts the cursor back on the control it was on after a re-render, and the two-line help bar speaks for the focused control through its `data-help`. A `.px-scroll` pane of words with no control in it may opt in with `data-reads` (the result screen's two do): while it overflows it is a cursor stop, and Up and Down read through it a row at a time (`readOn`) before the cursor moves on. So a row stays one or two lines and explains itself only when pointed at; a control that would do nothing takes `aria-disabled` rather than `disabled`, or the cursor can never reach it to say why. `refocus()` takes the same ordered selector list `focus()` does (`menuFocus.ts`), so a screen starts its cursor on what it is for, never on the way out.
- **Pointing at a thing is a question, and the answer is free.** The in-raid bag and party each bound their detail panel to one number, so the only way to be told what something was, was to choose it first: mid-raid, finding out what a RADIO VALVE is cost the row you were about to use. `src/game/ui/hoverDescribe.ts` is the rule, Phaser-free - a screen has three answers and the nearest wins, the thing the **pointer** is on, then the thing the **cursor** is on, then the thing the player **chose**, and neither pointing nor arrowing ever writes a selection, so the two inputs cannot fight. A thing says what it is with `data-describes="kind:id"`, so a pocket row and the square it takes up in the pack grid carry the same key and pointing at either answers for both and lights the other; a list carries `data-describe-group`, because the gap between two rows is a frame the pointer spends on the list itself and reading that as "on nothing" flickered the panel back and out again on every row it crossed. The answer is written **into** the panel rather than rendered - a pane is built per thing and all but one hidden - because the pointer is resting on a row while it runs, and a re-render flickers, re-fetches the portrait and can drop the control that was about to be clicked. Three things paid for in a browser. A live action **names the item it would spend** (`Use Potion`, never `Use item`), because the line above it is answering about whatever is being pointed at. `POINTER_ONLY` marks a thing the cursor may not describe, the rule behind it being that **the cursor may only describe something whose panel holds no controls of its own**. And a screen that hides controls must stop its arrow keys counting them (`control.offsetParent !== null`, in `MenuOverlay.cursorControls`), or focus refuses the hidden one silently and the cursor stops dead - which is true of every pixel-ui screen with a pane per row, the stash included. **The pixel-ui pass (#156) collapsed the three sources into one.** A pixel-ui screen has no selection: the cursor is the answer, the pointer moves the cursor, and moving it commits nothing, so finding out what a thing is cannot cost anything. At base the same key also drives a hover box (`ui/itemHoverHelp.ts`): resting the pointer on an item row or pack square for `HOVER_HELP_DELAY_MS` (0.7s), or the cursor on one, shows the item's catalogue name and description below it, inside the screen. What survives is the **key** - `describeKey`, on a pocket row and on the squares it occupies, which is what `BagScene.pointAtPack` and `markPack` read - and the hidden-control rule above. The rest of `hoverDescribe.ts` is kept with its reasoning against a screen that grows a selection again; its header says so. The field guide needs none of it: it has no selection and shows everything at once.
- The game screen is fitted to the browser by `src/game/display/stage.ts` and applied by `stageScaler.ts`: whole-number zoom only, and the room left over is spent on logical pixels (up to 400x256) rather than on margin; a window that cannot hold 640x480 (a phone) gets 1x, canvas and menus alike, because at 2x the canvas was squeezed thin and a panel's DONE ran off the edge. `applyStage` calls `resize` before `setZoom`, because Phaser writes the canvas's CSS size only when told a zoom and `resize` tells itself only at a zoom other than 1. At 480x360 or less the FEEDBACK tab is one small line in the corner. `BASE_STAGE_*` (320x240) is the smallest screen and the composition every scene is authored against - never lay anything out assuming more room than that. `WorldScene` uses the whole screen; `BattleScene` and `TitleScene` keep their authored composition, centred (battle by `centreComposition()`, which is why its coordinates are still plain battle-screen coordinates). `#app` is sized to the canvas in script and *placed* by it too, on whole pixels: the room left over in a window is odd as often as it is even, and letting the page centre the screen stood the canvas and every menu on half a pixel, which the browser resolves by blurring all of it. It also carries `--px`, one game pixel, for anything hung off the canvas box. - Phaser's key captures are global and outlive the scene that asked for them: `addCapture`, and `addKey` which captures by default, register on the game's KeyboardManager, so a paused `WorldScene` was still calling `preventDefault()` on O, P, B, K, SPACE and ENTER while an overlay it opened sat on top - which is why the field guide could only be closed with the mouse. Input ownership is therefore not a scene's to take: `src/game/ui/overlayKeyboard.ts` owns it, every `MenuOverlay` claims through it on construction and releases on `destroy()`, and one shared window listener in the *capture* phase gives the key to the topmost overlay and stops propagation so nothing below it - paused scene, Phaser captures, lower overlay - sees the key at all. Keyup is deliberately left to flow. A new overlay needs no key wiring of its own; It also swallows a *repeated* Enter or Space (`isHeldCommitKey`), default and all, because Chromium works the focused button on every auto-repeat and a held Enter once ran the drop-in step into the raid (`tools/playtest/heldEnter.mjs`). It also presses a focused button on Space's *keydown* (`pressFocusedButton`), because Chromium works a button with Space on the keyup and Phaser `preventDefault()`s the keyup of every captured key, so Space was dead on every menu. `isOverlayDismissKey(event, 'o')` is the shared rule that Escape and the key that opened a screen both close it, and `overlayKeyboard.test.ts` reproduces the whole layering without a browser. Every DOM menu rebuilds its markup per change and so must say where focus lands: `MenuOverlay.focus()` takes an *ordered* list of selectors (`src/game/ui/menuFocus.ts`), because one comma-separated selector focuses whichever match is first in the document, and that is always the back button - whose Enter resumes the raid clock. - One typeface, and it is a load-time dependency: `GAME_FONT` in `src/game/ui/gameFont.ts` is the only family any canvas scene names, `index.html` preloads the woff2 with the document, and `BootScene.create()` waits on `awaitGameFont()` before starting a scene. Sizes for the raid screen are `src/game/ui/screenType.ts`, picked to hold the letter heights the HUD was designed at rather than the numbers that used to be typed. Canvas text is hard-edged because `installPixelText()` (`src/game/ui/pixelText.ts`, called from `main.ts`) replaces every Phaser `Text` context's `fillText`/`strokeText`/`measureText` with a run-time bitmap font: each glyph is rasterised once in a fixed ink (Chrome antialiases white text heavier than black, so a glyph measured in one colour and painted in another came out a pixel different), thresholded by `inkMask` - which keeps a thin stroke that fell across two pixels as one - and stamped ink-tight at whole-pixel advances. Orange Kid is an outline face whose own grid is about 12.5px: it does not survive below 12px (`W` reads `V`), and at 16-18px stems are a pixel and a quarter, so one word mixes one- and two-pixel letters and the gap under a dot closes (`kit is` read `klt ls`, `appeared!` read `appearedl`). `screenType.ts` holds the sizes that come through whole - 12px chips and captions, 14px for the clock, dialogue and commands - so name one of those rather than typing a number, and check any new size on a specimen of lowercase and punctuation first. A change to how a glyph is cut (`inkMask`, the threshold, the nudges) is judged glyph by glyph with `tools/playtest/glyphSheet.mjs --against=`, which prints every one of the 336 renderings it changed: the rule that keeps a split stroke's end so `S` is not `3` changes 8, and a looser first draft changed 198. An accented letter (`isMarked`) leaves the setting the rest of the face uses only where that setting ran a mark into its letter or another mark (`inkPieces` against the glyph drawn four times the size), searched across and never up and down, so a diaeresis stays two dots and no plain letter moves; `glyphSheet.mjs --chars=accents` sheets the letters a map may use. `gameFont.test.ts` fails any scene or widget that names a family literally - the title, party and bag scenes all named `monospace` while the rule was checked against three files.
