# Online services

The FEEDBACK tab, the Supabase project (submissions, sign-in, publishing, review) and play counting.

Moved out of `AGENTS.md` on 9 Nov 2026 so that file stays small; nothing here was reworded. Keep it current the way `AGENTS.md` asks: a change that adds a subsystem or makes a note here untrue updates the note in the same change, and a new note goes in the doc whose area it belongs to.

## Notes

- **A player tells us what happened through the FEEDBACK tab** (the owner's plan, agreed on the board 2026-10-10). `feedback/feedbackDesk.ts` is the tab (a page element beside `#app` and `#screens`, so it is on every screen) and the F key (a window capture listener installed before any overlay claims the keyboard, so F reaches it first on every screen and never from a text field, nor in the map maker, whose F is FILL - `isFeedbackKey`); pressing either asks Phaser for a snapshot (not on a menu screen, which is drawn in the page over the canvas, so its picture would be the black behind it), writes down where the player is, **pauses every running scene** - which stops the raid clock with the raid - and runs `FeedbackScene`, whose close resumes exactly those scenes and nothing else. Where the player is comes from the screens themselves: a scene with a `feedbackContext()` (`ProvidesFeedbackContext`) is asked at the press, running or paused, and `feedback/actionLog.ts` keeps the last thirty things that happened (screens started, menu buttons pressed by their words, places walked into, fights, page errors - never anything typed). Every word the panel says is `feedbackWords.ts`, in the raid's voice, with the tag on every ending; the tab alone says plain FEEDBACK. TALK is `feedback/voiceTape.ts`: press once to record and again (or SEND) to stop - the owner's ruling, never hold-to-talk - up to five minutes across any number of clips, Opus at speech bitrate (~180 KB a minute), and the microphone is open only while it records. A message is put in the browser's IndexedDB outbox (`outbox.ts`) **before** any send is tried and taken out only once the lab holds it (`courier.ts`), over five a day it is held for tomorrow rather than refused, and the pack is flushed five seconds after the game opens and on the browser's `online`. The lab is the map maker's Supabase project (`feedbackSender.ts`): an anonymous session uploads the picture and clips into `feedback/<its id>/<tag>/` of a private bucket and calls `submit_feedback`, which re-checks that every file is the caller's, holds five a day per player and a hundred overall, and answers a tag it already holds without storing it twice - so a retry is always safe. A player can read nothing back. The far end is `tools/feedback/collect.mts` on the owner's PC (`tools/feedback/README.md`): with the service-role key it turns each new message into a folder (naming every file itself, by what its first bytes are - nothing a player sends names anything on the PC, and player text sits in code blocks), marks it received, deletes its voice from the project at once, anything received over ninety days ago, uploads no message names and long-idle anonymous visitors with nothing in the lab - both asked of the project itself (`unclaimed_feedback_uploads`, `idle_anonymous_visitors`), because the Data API cuts every read at 1000 rows and a safety list built from a slice deleted the players outside it (red team F5); every other read is paged, and a message that will not download is left for the next run - turns clips into text with `transcribe.py` (faster-whisper, local; a clip it cannot read gets `transcribe-failed.txt` and never stops the rest, and only exit code 3, not installed, stops the run), writes `index.html`, and prints one line only when something is new - tags, screens and kinds, never a player's words, because an agent reads it (`inbox.ts`). The build is stamped by `vite.config.ts` (`buildInfo.ts`). `tools/playtest/feedbackShots.mjs` plays it end to end; `docs/screens/feedback/`.
- **Player maps are sent to the game's own Supabase project, `pallet-town-maps`** (ref `ejdazksxwwiubudkkvaj`, eu-west-2; URL and publishable key in `maker/submitConfig.ts`, public by design). The schema lives in `supabase/migrations/` and is applied with the Supabase MCP tools - keep every applied migration there byte for byte, **named by the version `list_migrations` reports**: `apply_migration` stamps its own (the moment it ran), so a file written ahead with a guessed number is renamed once it is applied. A player has no account: **every sign-in is `maker/playerSignIn.ts`** - the FEEDBACK tab's SEND, the map maker's SEND and a console score, never anything that only looks - and every one passes a fresh invisible Cloudflare Turnstile token (`maker/turnstile.ts`, site key in `submitConfig.ts`, script fetched on the first sign-in; the project ignores a token until the owner switches captcha protection on in Authentication > Attack Protection, so a build never waits on that switch). A check that would not load or did not pass is said in each place's own voice and keeps what was being sent to try again (the pack, the drafts, `console/leaderboard.ts`'s `WaitingScores`); the background courier never signs in, because nobody is looking at a check there. `@supabase/supabase-js` is lazy-loaded so nobody else downloads it. **A player can only call `submit_map`, `my_submissions`, `reserve_feedback_uploads`, `submit_feedback`, `submit_console_score`, `console_leaderboard`, `name_my_house` and `harbour_names` (the boards and the harbour's names signed out too, so looking signs nobody up), and `record_play`, which is *only* signed out (see the play-counting entry), and upload into their own folder of the private `feedback` bucket under a name `reserve_feedback_uploads` handed out** - counted under a lock, because a count inside a storage policy races a burst (red team F7), in files and in bytes (`upload_byte_budget`: a name with no file yet counts at the bucket's size limit, one that has its file at its real size, so the budget is exact under the lock; 32 MB a player, 200 MB for everybody, a day); the collector's `unclaimed_feedback_uploads` and `idle_anonymous_visitors` are the service role's alone. A new function starts shut wherever it is created (the global `alter default privileges ... revoke execute on functions from public` - a per-schema revoke never reverses PUBLIC's EXECUTE), and every migration still revokes its own; `maker/functionGrants.test.ts` holds both and the short list of functions open to a signed-out visitor; anonymous sign-ins are on, so every admin policy also refuses an anonymous token in its own text (`admins_not_anonymous`), no role holds a grant it does not use (`feedback_security_tidy`), and `node tools/supabase/anonymousProbe.mjs` tries every door from outside, signed out and then as a fresh anonymous player - run it after any change to a policy, grant or function; with captcha protection on it checks that signing up without a token is refused and needs `TURNSTILE_TOKEN` from a check passed by hand to ask the signed-in doors. Against the real project it is read-only (its `--send` and `feedbackShots.mjs --live` write rows no player can take back, so they run against a stand-in); what a function accepts is checked as an anonymous user inside a transaction that is rolled back. The MCP refuses `drop` and `delete`: change with `alter`/`revoke`, and mark rows rather than remove them; the table has no policy a player matches, only admins (`public.admins`) read or update it, and the privileged code is `security definer` in the unexposed `private` schema behind `security invoker` wrappers in `public` (lint 0029 - run `get_advisors` after any change; it must stay empty). `submit_map` checks shape and size against the format's own `MAP_FILE_LIMITS` (256x256) and refuses any key outside `MAP_FILE_KEYS` and `< > & "` in either name, so nothing a reviewer cannot see rides an approval into the repo; **a new key in `MapFile` needs a migration that rewrites `submit_map`'s list in the same change** - `maker/submissionLimits.test.ts` fails to compile on a key `MAP_FILE_KEYS` lacks and fails on a migration that disagrees with it. It enforces 3 maps a maker a day and 300 overall, one call at a time (an advisory lock, so the counts are exact). **Publishing** is `.github/workflows/publish-player-maps.yml` (half-hourly and by hand), four jobs because the steps of one job share a machine (red team F2): `fetch` and `mark` hold the `SUPABASE_SERVICE_ROLE_KEY` secret and run only `tools/maps/projectRequests.mjs`, which imports nothing but Node's own modules and installs nothing; `verify` holds no secret and may only read, and is the one job that runs `npm ci --ignore-scripts` - `publishApproved.mts -- prepare` (`tools/maps/prepareMaps.ts`) runs `readMapFile` and `checkMapFile` again (a map that fails, or that throws, is listed to be sent back with the reasons, never stopping the maps behind it), writes each as one file in `src/maps/player/`, then lint, typecheck, the suite and the build; `publish` holds the write token, installs nothing, commits only files named as map ids, opens and merges its own PR and starts CI on it by hand, whose pass deploys the game - a change made with the workflow's own token starts no other workflow; `mark` records `published` (only once merged) and the send-backs, only for submissions `fetch` read and ids of the right shape. `tools/maps/publishWorkflow.test.ts` holds all of that. `SUPABASE_URL` points the scripts at a local stand-in. With no key `fetch` **fails the run** rather than publishing nothing in green. Branch protection on `main` is the owner's to switch on (a ruleset bypass for the bot, or the merge stops). A published file's name comes from `freeMapFileId` (`mapFile.ts`): never a sample's id, a reserved one, or **any id the project has ever recorded** (`recorded-ids.json`, red team F12), and cut short before `-2` so it stays within the 40-letter id limit. **A fix to a map in the game replaces it** (the owner's call on playtest 35, option a): `submit_map`'s `resubmits` may name the maker's own published row, the new row carries that map's `map_file_id` (recorded by `mark` for every published map), the reviewer's row and pane say UPDATE, and `prepare` writes it over the same file through `keepPublishedIds` - only while that file is still in the game and the newest published row under it is the same maker's - - same map id, and every published drop-in keeps its id by name, then tile, then order - so nothing a player holds on the map is lost. **Reviewing** (`maker/review.ts`, the map maker's *Review maps* panel under Drafts) is the owner signing in with GitHub on a client of its own (`reviewSupabase`), whose session lives in `sessionStorage` (forgotten with the tab, ended on the server only by SIGN OUT, which is `signOut({ scope: 'global' })`), because the game shares its origin with every other ollysalanson.github.io page and an admin token in `localStorage` would be theirs to read; the player's client never reads a sign-in from the address (PKCE; the return lands on `?review=1`, which `TitleScene` sends straight to the review list): a trigger grants `public.admins` to the GitHub identity with provider id `40039465` (the owner's account id, never a name or "first to sign in"), and the database holds that as the rule rather than the habit of one trigger (`admin_is_the_owner`: a row for any other user is refused, and `private.is_admin()` asks for the identity as well as the row, so a stray row counts for nothing; `maker/ownerAdmin.test.ts`), and a reviewer may update only `status`, `owner_note`, `map` and `map_name`. A map is opened into the editor as a draft of the reviewer's own, played with TRY IT, fixed if needed, and approving takes the map as it then stands. Auth settings (anonymous sign-ins, captcha, redirect URLs, the GitHub provider) are dashboard settings no migration holds; `signInToReview` asks `/auth/v1/settings` before redirecting, so a switched-off provider never strands anyone on an error page.
- **Play is counted, for the owner's STATS page, and nothing personal is kept** (the captain, 2026-10-12: "so I can see if anyone actually plays"). `analytics/playCounter.ts` batches a handful of moments - `visit` (one a page load), `starter`, `raid-start` (a shipped map's id, any player map as `player`), `raid-end` (`extracted`/`wiped`/`clock` from `ExtractionScene`, `abandoned` from `BaseScene`'s settle), `played` seconds (visible and touched in the last five minutes), `map-sent`, `blocks`, `harbour` (once a page) - and posts them with a plain `fetch` to `record_play`, **signed out**, so counting never loads supabase-js, signs a visitor up or asks the bot check; anything that fails or finds the browser offline is dropped. It sends nothing unless `shouldCount` (a production build, not test mode, at the published address only, not an automated browser - `isAutomatedBrowser`: `navigator.webdriver` or a headless/crawler agent - no Do Not Track or Global Privacy Control), nothing from a TRY IT raid, and **nothing at all until a trusted key or click** (`PlayCounter.heardFrom`): the first night's six "players" were link scanners on cloud addresses in made-up browsers, and only that gate catches the ones that lie about their agent. A **tester** is counted apart (`*_play_testers.sql`): a browser marked by `?tester` once (`followTesterLink`, `?tester=off` undoes it) or by the switch on STATS (which marks the owner's browser the first time it loads the counts) sends `tester: true` with every batch, the visitor row's `cohort` follows the last word, and its moments land in `play_daily` as `tester:<metric>`; `automated` is a cohort only a migration writes, for rows the logs prove were machines (`automated:<metric>`). Every real metric has no colon in its name, which is how `play_stats` keeps the headline numbers real players only. To ask what a count was, the API's own edge logs (`query_logs`, `edge_logs`, path `record_play`) carry the time, user agent and network of each batch for a day; nothing of that is stored. The database is the only check (`*_play_counts.sql`: every field from a fixed list, fifty a batch, six hundred a day a browser id, a hundred thousand a day in all, counted on the rows they bump) and keeps **no raw events at all**: one row per random browser id (first, last and previous day seen, days seen, moments today) and `play_daily` totals, so there is nothing to prune - which matters because **the Supabase MCP stops any statement with `delete` in it for a human to confirm, even inside a function body or a rolled-back transaction** (`execute_sql` answers "Invalid or expired requestState"), so an unattended worker cannot ship pruning. A new moment is a kind in that function's list (a new migration) and in `PlayMoment`; `playCounter.test.ts` holds the two lists together. The page is `StatsScene` (markup `analytics/statsView.ts`), opened by `?stats` on the address or PLAY STATS on the map maker's review list, reading `play_stats`, which refuses anyone but an admin and also counts **named players** straight from `public.player_houses` (a house is made the first time a name is chosen at NEW GAME, so its `created_at` is the sign-up) rather than copying names into the play counts; its GitHub sign-in is the review one, returning to the same `?review=1` with `rememberSignInDestination('stats')` in session storage, so no new redirect URL is needed.
