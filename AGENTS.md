# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Update this file in the same change whenever work adds a subsystem, changes where something is registered, or contradicts a note below. This is part of finishing the task, not optional cleanup.
- **This file holds only what almost every task needs; each area's detail is a doc under `docs/agents/`**, listed at the end with when to read it. Read the doc for the area you are working in before changing it, keep its notes true in the same change, and put a new note in the doc whose area it belongs to - never back here, unless almost every future task needs it. This file must stay well under Claude Code's 150,000-character limit for a memory file (it was 446,714 characters on 9 Nov 2026, three times over, and every worker paid for it in context).

## Working on this repo

- **The pull request's checks are the gate, and the full suite never runs on this PC** (the captain, 30 Oct 2026: it was each worker 13 minutes or more through one shared slot, and a bad merge only went red on main, which blocks publishing). `.github/workflows/ci.yml` runs lint, typecheck, build and the whole suite (four `--shard`s side by side) on GitHub's machines, for every pull request to `main` and on `main`. A worker runs locally only `npm run lint`, `npm run typecheck` and the tests its change touches (`npx vitest related <files> --run --maxWorkers=2`), never the whole suite nor a vale sweep (`mapStructure.greystoneVale*.test.ts`, `hunterFlee.test.ts`), so nobody queues for anything; a pull request merges only when its `ci-passed` check is green. Wherever a note below says to run or re-run a sweep, the pull request's checks are what run it. `pages.yml` tests nothing: `publish-after-ci.yml` starts it when CI passes on `main`, and it builds and deploys the newest commit on `main` that passed (`docs/deployment.md`), so CI failing on `main` holds publishing at the last pass. A change made with a workflow's own token starts no other workflow, so `publish-player-maps.yml` has its own `verify` job and asks for CI on its merge by hand.
- **Bring a branch up to `main` with a merge or a rebase, never by copying files over it.** #472 was rebuilt on a newer `main` with its files carried across whole, and its squash merge quietly put back the older text of 69 files and deleted 28 more, undoing #470 and #471 while CI stayed the colour it was. Before marking a PR ready, `git diff --stat origin/main...HEAD` must name only files the change means to touch.
- Driving the real game end to end: `npm run dev -- --port <free port>` plus Playwright's Chromium, launched by `tools/playtest/browser.mjs` (`ensure-libs.sh` beside it supplies the `libnss3`/`libnspr4`/`libasound2t64` that Chromium needs, without root), and CDP `Input.dispatchKeyEvent` for keys. A tap is enough everywhere - Phaser scenes through `KeyPresses`, DOM menus natively - and `raid.mjs --taps` plays a whole raid on down-and-up-back-to-back presses to keep it so. `tools/playtest/` is that recipe packaged (`README.md` there: test modes, stepping, hygiene, and `--insertion=`/`--beaten=`/`--completed=`/`--level=`/`--work=` for deploying to any map, with a team that could have got there, and reaching any ending); `raid.mjs` plays a whole raid and picks its exit by walked distance, because an exit can be open by its own rule and behind a shut gate. `raid.mjs --read=itemId` reads a disc in the raid's own bag (the only place a machine is ever used) and `--open=LABEL` works a field-move door, which is the one thing that changes a map's collision without a battle or a warp between; `--grab=itemId` walks to every piece of that item *this* raid laid, read off the run plan, and `--secure=itemId[:n]` takes the secure-slot detour on the way out: loot is re-seated every raid and the container reserves room by kind, so nothing else can check either end to end. A driver that steps the loop itself must know the three states in which nothing is on screen to press through and the world is about to change anyway - an authored beat running (`WorldScene.cutscene` - the watch's mark and walk-up is one), the fight queued behind the last line of dialogue, and `WorldScene.isWarping` while the hand-over to the battle fades - or it stops stepping mid-beat and asks the map a question the fight is about to change the answer to; `raid.mjs`'s `pendingBattle` is that, and without it a boss fight simply never happened. A driver that pauses the loop also hands `deploy` and `walkIntoBase` its own `wait`: the base walk used to settle on a real-time sleep, which moves a paused game by nothing, and every stepped driver (tour, gridtour, interior, whyHidden, `raid.mjs --stepped`) stalled on Oak's Lab's doorstep for two days before anyone noticed - `walkIntoBase` now refuses a paused loop without one (`deploy.test.mjs`). `window.__escapeFromPalletTownGame__` (from `gameLifecycle.ts`) reaches every scene, so `scene.getScene('world').collisionData` gives a real map to path through and `getScene('battle').state` is the battle to assert against; seed `localStorage['escape-from-pallet-town.save.v1']` to start from a state that would otherwise take a long grind to reach.
- Browser checks are rationed, because six workers each holding a 60fps game under software WebGL is what got processes OOM-killed on this box. `tools/playtest/README.md` is the recipe and the measurements (the same raid: 40 CPU-seconds plain, 2.9 in test mode, 1.2 stepped); `tools/playtest/browser.mjs` is the launch - do not restate either. The rules: one browser per verification session, closed when its checks are done, and the dev server stopped with it; never a live game page while thinking or editing (`pauseLoop()`, or drive the check with `stepFrames` so it never runs live at all); the CDP port comes from the OS (`--remote-debugging-port=0`), never a fixed number, because another worker is on it; everything at niceness 15, which the tools now do themselves (`tools/lowPriority.mjs`, called by `launchBrowser()` and by `vite.config.ts` and `vitest.config.ts`, so a new browser or heavy tool goes through one of those or calls it - asking workers to type `nice` was measured not to work); `?testmode=1` for every logic check, `?testmode=pixels` for a screenshot, and a screenshot session against a test-mode **build** rather than the dev server (a dev page passes 1GB on the title screen; the README's 'Memory' section has the numbers and how to serve one) - Phaser's Canvas renderer draws no tints, so a `?testmode=1` frame shows grass where the water is - and one plain-URL pass at real speed before reporting done. Test mode is `src/game/dev/testMode.ts`: a development-build URL flag (`VITE_EPTW_TEST_MODE` for a build), so production cannot be put into it. `vitest.config.ts` caps the suite at four workers for the same reason; `VITEST_MAX_WORKERS` raises it. **Whole-map sweeps are where a growing map bites the suite**: it went from three minutes to fifteen as the maps grew four times over, nearly all of it one file of searches asked from every tile of every map in every gate state on a single worker while the other cores idled. What brought it back, and the pattern for the next sweep: **split a sweep into files**, because vitest runs files side by side and never the tests inside one - the structure rules are `mapStructure.testkit.ts`, asked by one `mapStructure.*.test.ts` per map and per third of the Floodplain's gate states (`MAP_STRUCTURE_PARTS`; `mapStructure.testkit.ts` fails a gate state no file asks about, so a new map is a row and a file); **hand a whole-map search `collisionBlocker(map.collision)`** rather than a callback, which reads the grid once and gives `hunter.ts`'s searches a neighbour table; and **take work that does not depend on the loop variable out of the loop** - `planHunterBreakaway` is the flee's searches once for all four headings, `it.each(insertionIds)` gives each landing its own budget, a search repeated per destination is memoised per player (`hunterFlee.test.ts`), and a sweep of thousands of raids gathers its faults and asserts once rather than calling `expect` ten thousand times. None of it weakens what is asked: the searches were diffed against the old code tile for tile.
- Anything the world times for itself must survive a 100ms frame, because that is what test mode hands it. Walking did not: a step could only end on a frame and the rest of that frame was dropped, so a tile cost 150ms of raid clock at 60fps and 300ms at ten. `src/game/movement/stepClock.ts` carries the overflow into the next step (`STEP_DURATION_MS` is the one number a tile costs, at any frame rate) - and a step that ends part-way through a frame begins the next in that same frame, in `WorldScene` and `BaseScene` alike, because begun a frame later the walk stood still for one frame and doubled the next, once a tile, and the camera shook the whole map with it (playtest 28 F1; no game time is lost, so only `tools/playtest/walkJudder.mjs`'s per-frame distances show it) - and a press shorter than a frame is kept too: a scene that polls keys loses one both ways, because `isDown` is false again and `Key.onUp` clears the flag `JustDown` reads. `src/game/input/KeyPresses.ts` is what `WorldScene` and `BattleScene` ask instead of `Phaser.Input.Keyboard.JustDown`, and `pressLatch.ts` beside it is the rule - a press is kept for the frame that processed it and no later, so one made under a dialogue or mid-step is still dropped. A new scene that polls a key goes through `KeyPresses`; a new per-frame `Math.min(1, progress + delta / duration)` is the other pattern to distrust. Phaser's own timers and tweens were already safe.
- Phaser reuses ONE instance per scene key for every `scene.start`, so any field describing the raid in progress outlives that raid. Clear per-raid state on entry - `WorldScene.resetStateFromPreviousRaid()` is that list, `BattleScene.create()` and `HubScene.applyLoadedGame()` are the equivalents - and add to it rather than guarding the read. A missed `pendingHubTransition` reset made every raid after the first unplayable; `consecutiveRaids.test.ts` drives two raids on one instance to guard it.
- `HubScene.init()` prefers the stored save over its start payload: Phaser hands a restarted scene its previous payload when `scene.start('hub')` passes none, which otherwise re-renders a pre-raid snapshot after extraction. **Two tabs share one save**, and the hub is the one screen that writes its own whole copy of the game (the Pokemon Center's recovery, treatment, gear, boxes and the move chooser all go through `HubScene.writeGame()`): it remembers `SaveManager.stamp()` - the raw stored text - when it reads the save, and `movedOnElsewhere()` refuses an action and catches the screen up if storage has moved on since, because written over a newer save it erased a banked contract or undid a wipe - and `startRun` asks it too, or a loadout built before a wipe in the other tab deployed the Pokemon and gear the wipe took. Every other write is a `SaveManager` method that loads first; a new screen that keeps a copy must do one or the other. `tools/playtest/staleTab.mjs` plays the two tabs. And a fresh second tab is no safer than a stale one while a raid is out: the raid owns the Pokémon it took and what it packed until it ends (`RaidInFlight.pokemonIds`), `SaveManager.save` refuses any write that would change them (`raidHoldRefusal`), and every ending names its raid (`ActiveRunSession.raidId`) and settles only that one - a new base action on a Pokémon or a supply asks `awayOnRaid`/`spareAtBase` first to say so (`docs/agents/raid-and-stash.md`; `tools/playtest/twoTabRaid.mjs`).
- Active raid scene data is defined by `ActiveRunSession` in `src/game/run/RunSession.ts` and must pass unchanged between `WorldScene` and `BattleScene`. What lives only on `WorldScene` - the hunter, beaten trainers, taken loot, worked landmarks, the return tile - is `RaidCarriage` in `src/game/run/raidCarriage.ts`: a battle shuts the world down and the world is rebuilt from what the battle hands back, so anything not in that payload is forgotten. `WorldScene.raidCarriage()` packs it once for every kind of fight (a call site names only the fight), `BattleScene` must hand back a whole one, and every key is required, so new per-raid world state is added to the interface and the compiler names each place that must carry it. A hand-written wild payload two fields short of the trainer one is how every wild fight re-announced the hunter and stood beaten trainers back up; `consecutiveRaids.test.ts` drives the real round trip through both scenes. The bag, party and field guide pause and resume the world, so they rebuild nothing.
- `SaveManager` accepts seven save versions, and accepting one is a promise to honour everything in it. Versions 1 to 3 were written by the free-roam game, where the player's team was `party` and their supplies were `bag` - fields the extraction game never reads, because the vault is the team. Loading one used to say yes and hand back an empty vault, which `Stash.ensurePlayable()` filled with a fresh level-5 starter and `TitleScene` wrote back over the file, destroying a levelled team without a word. `moveFreeRoamHoldingsIntoVault()` in `SaveManager.ts` is the migration, gated on `LAST_FREE_ROAM_SAVE_VERSION` and on the vault being entirely empty - the signature of a free-roam save and of nothing else - and it moves rather than copies, so nothing is banked twice. Versions 4 and 5 are deliberately untouched: there an empty vault means a wipe, and the fresh starter is the intended answer. Every accepted version is pinned in `SaveManager.test.ts`; a new version must be added there as well as to the accept list.
- Scenes are registered in `src/game/gameConfig.ts`, not `main.ts`.
- `Pokemon` has no `cureStatus()` method; clear a status by setting `primaryStatus` to null directly, which `SaveManager` saves and restores.
- **Only Greystone Vale is in play** (the captain, 2026-10-22: the five maps drawn the old way are put away, not deleted, and may come back). `world/mapRoster.ts` is the one switch: `RETIRED_MAPS` lists them and `isMapOffered` is the one question, asked by `availableInsertionIds` (no landing on a retired map is offered, whatever the save holds, so a save whose every landing was on one is turned to the vale's front door), by `availableContracts` (a contract on a retired map is put away with it, so the chain is finished before it starts and the standing board deals on the vale), and by the wall map, pennants and badge case. Bringing a map back is taking it off that list. **The suite runs with nothing retired** (`mapRoster.testkit.ts`, a setup file), so every rule still holds the retired maps fit to return and every test written about the chain still asks it; `world/mapRoster.test.ts` and the last block of `HubScene.test.ts` put the shipped list back (`retireMapsForTests`) to ask what a player is offered.
- `public/assets/ASSET_PROVENANCE.md` records where every shipped asset came from, who authored it and under what licence; adding an asset without its entry there is an incomplete change. Most of it is carried over byte-identical from the captain's Unity project `OllySalanson/escapeFromPalletTown` (blob SHAs, re-checkable with `gh-axi api`); `Overworld.png` and `character.png` are traced past it to ArMM1998's CC0 pack and proved by hash; the icons were drawn here, and `battle/orange-kid.woff2` comes from Typodermic's own CC0 page. `frlg-tiles.png` and `characters/*.png` are ripped FireRed/LeafGreen art the captain accepted knowingly on 2026-09-19 - cut frames only, never a Spriters Resource sheet in the format it was downloaded in, and never onto a marketplace. Two files are flagged as unsettled: `battle/background-grass.png`, and `tileset.png`, whose origin is not established and which the pixels say is GBA Pokemon-family art. Verify at the publisher rather than assume, and never resolve a flagged question in code instead of in that file.
- **README.md is the public front page and a showpiece**, written in a warm, cheeky voice for players first and developers last; it names no studio. Every claim on it is checked against the code or the screen, so a change that makes one untrue (the clock, the cast, a key, a map) updates it in the same change. Its pictures are the game's own, made by `tools/playtest/readmeShots.mjs` and `tools/readme/drawArt.mjs` against a test-mode build, 800 wide (or 1600 shown at half) because GitHub's column is 838; `docs/readme/README.md` says how to make each one again. The rest of the GitHub page speaks in the same voice - the About line, `CONTRIBUTING.md`, the issue forms and the PR template under `.github/` - and so does the link preview, `docs/readme/social-preview.png` (drawn by `drawArt.mjs`, uploaded by hand under Settings because GitHub has no API for it).
- **GitHub Pages** publishes the static client from `main` once CI has passed (`.github/workflows/pages.yml`) at `https://ollysalanson.github.io/escape-from-pallet-town-web/`. Production builds set Vite `base` in `vite.config.ts`; runtime asset URLs go through `publicAssetUrl()` in `src/game/publicAssetUrl.ts`, and a stylesheet names a public file root-absolute (`url('/assets/...')`), which the dev server serves as it is and the build prefixes with `base` - a relative one resolves next to the built CSS but against `/src/` under `npm run dev`, which is how local play lost the font and the figure sheet after #166. `src/styleAssets.test.ts` asks Vite both ways. See `docs/deployment.md`.
- **Generated and drawn files are rebuilt, never edited or hand-merged.** Greystone Vale ships as `src/game/world/maps/greystoneVale.json`, stitched from the district programs under `tools/mapcraft/worlds/greystoneVale/`: edit a program and write the file again (`npx vite-node tools/mapcraft/world.mts -- tools/mapcraft/worlds/greystoneVale/index.ts out/greystone-vale --shrink=3 --write=src/game/world/maps/greystoneVale.json`), and on a merge or rebase conflict in it take the merged programs and write it again rather than resolving the JSON by hand - `worlds/greystoneVale/greystoneVale.test.ts` fails a file that is not what the programs draw. The same holds for everything under a `generated/` folder (species, moves and machines from `node tools/species/generate.mjs`, `world/generated/` from `tools/encounters/`, `base/generated/` from its `scripts/cut-*`/`draw-*` script or `tools/base/botSpots.mts`), for sheets a script draws (`raid-arena.png`, `promenade.png`, `arena-hall.png`, `great-library.png`: edit the script), for `src/game/console/vendor/` (`scripts/fetch-console-games.mjs`) and for an applied Supabase migration, kept byte for byte. Each area doc below names its own generator.
- **A test never counts the shipped maps, and runs with nothing retired.** The suite always has one approved player map in it (`world/publishedMapFixture.testkit.ts`) and puts every retired map back (`world/mapRoster.testkit.ts`), so ask `deployableMapIds()`, `frontDoorFor()`, `extractionPointsOn()` and `insertionsOn()` rather than a literal count, and use `retireMapsForTests` to ask what a player is offered. Seeded rolls share streams across maps, so adding a thing to one map can move another map's roll: make a test ask for what it means rather than tune a map round a lucky seed (`docs/agents/world-mechanics.md`, the loot pool note).
- **Show, don't tell, and keep the front page true.** A change to anything on screen puts a before and after picture in the pull request, usually under `docs/screens/<topic>/` with a README saying how it was made; a change that makes the README, `CONTRIBUTING.md` or a book in THE GREAT LIBRARY (`library/books.ts`) untrue updates it in the same change.
